# i18n Design

Date: 2026-09-26

## Goal

App has zero i18n today: no locale detection, no locale switching, no
frontend translation library, only `en.yml` / `devise.en.yml` exist and are
used ad hoc for two flash messages. Add full i18n infrastructure across
backend (Rails views/flash/mailers), API (session-authenticated items API,
Swagger docs), and frontend (Inertia + React pages), shipping with `en`
only but structured so adding a second locale later is data-only (new yml
+ json files, zero code changes).

## Locale resolution

No URL prefix (`/en/...`) — locale is invisible in the URL, carried via
cookie/session only. No per-user stored preference for now — every
visitor, signed in or not, resolves locale the same way.

Priority chain, applied identically to Inertia page requests, plain-MVC
(admin) requests, and API requests:

1. `locale` cookie (set when a user explicitly picks a locale via the
   locale-switcher endpoint)
2. `Accept-Language` request header (best match against
   `I18n.available_locales`)
3. `I18n.default_locale` (`:en`)

A per-user stored preference (`users.locale`) is deliberately deferred —
can be added later as a small follow-up (new column + one more step at
the top of the priority chain) without touching anything else in this
design.

Resolution happens once per request in `ApplicationController`, so it
applies uniformly to `InertiaController`, `AdminController`, and API
controllers without each needing its own logic.

## Backend

### Schema

No schema change. Locale is resolved purely from cookie/header per
request; nothing is persisted to `users`.

### Locale resolution concern

`app/controllers/concerns/sets_locale.rb`, included in
`ApplicationController`:

- `around_action :switch_locale`
- `switch_locale` resolves via the priority chain above and wraps the
  action in `I18n.with_locale(resolved_locale) { yield }`
- Resolution helper checks, in order: `cookies[:locale]`,
  `http_accept_language.compatible_language_from(I18n.available_locales)`
  (via the `http_accept_language` gem — new dependency), `I18n.default_locale`
- Only locales in `I18n.available_locales` are ever accepted from a cookie
  or header value, to avoid `I18n::InvalidLocale`

### Explicit locale switching

New endpoint, `PATCH /locale` (`config/routes/locale.rb`, drawn from
`routes.rb` alongside the other route files):

- Params: `{ locale: "en" }`
- Validates against `I18n.available_locales`
- Sets `cookies[:locale]` (long-lived, e.g. 1 year)
- Responds `head :no_content` for API/fetch use; the frontend locale
  switcher calls this then reloads the current Inertia page (via
  `router.reload()`) so shared props re-render in the new locale

### Translations

`config/locales/en.yml` (existing) stays the source of truth for
backend-rendered strings: flash messages, Devise strings
(`devise.en.yml`, existing), API error messages, mailer content. No
change to the existing yml structure — just more keys as they're needed,
and a second locale later is `config/locales/vi.yml` +
`devise.vi.yml`.

### API error messages

API controllers (`app/controllers/api/`) already return JSON error
bodies — these get run through `I18n.t` for the message text so
`Accept-Language` on API clients (Swagger UI, curl, etc.) works without
any session/cookie. No change to error response shape, just to how the
message string is produced.

## Inertia bridge

`InertiaController` gains one more `inertia_share`, alongside the
existing `flash` and `user` shares:

```ruby
inertia_share locale: -> { I18n.locale.to_s }
```

The frontend reads this on every page load/visit to keep i18next's
active language in sync with the server-resolved locale, so first paint
never flashes the wrong language and locale stays consistent across
Inertia partial reloads.

## Frontend

### Library

`i18next` + `react-i18next` (new npm dependencies).

### Structure

- `app/frontend/locales/en.json` — flat/nested key JSON, one file per
  locale, mirroring the pattern of `config/locales/en.yml` but
  independent from it (separate source of truth by design — backend and
  frontend strings don't overlap in practice: one is server strings,
  the other is UI copy)
- `app/frontend/lib/i18n.ts` — i18next init: registers the `en`
  resource bundle, sets initial language from the Inertia `locale`
  shared prop (read at bootstrap in `app/frontend/entrypoints/inertia.tsx`
  before the first page renders)
- Inertia's `router.on('navigate', ...)` (or equivalent lifecycle hook)
  syncs `i18next.changeLanguage()` if the shared `locale` prop changes
  between visits (e.g. after the user hits the switch-locale endpoint
  and the page reloads)

### Usage in components

Standard `react-i18next` `useTranslation()` / `t()` calls in page and
UI components. No new abstraction layer beyond what the library
provides — YAGNI given single-locale launch.

## Locale switcher UI

A small dropdown/select component (visible in the shared layout, e.g.
next to the existing user menu) listing `I18n.available_locales`
(currently just `en`), calling `PATCH /locale` on change via
`js-routes` helper, then `router.reload()`. Scaffolded even with one
locale so the plumbing (endpoint, cookie, DB column, frontend call) is
exercised and tested now rather than added later untested.

## Testing

- Request spec for `PATCH /locale`: sets cookie, rejects invalid locale
- Request spec asserting `Accept-Language` header changes `I18n.locale`
  when no cookie is present
- Request spec asserting cookie wins over a differing `Accept-Language`
  header
- Frontend: a vitest unit test for `lib/i18n.ts` initialization reading
  the `locale` prop
- No translation content correctness tests (single locale, `en` keys
  mirror existing English strings)

## Out of scope

- Per-user stored locale preference (deferred, see Locale resolution)
- Any second locale's actual translated content (structure only)
- URL-based locale routing
- RTL layout support
- Locale-aware number/date formatting beyond what `I18n.l` / `Intl`
  already provide out of the box
- Translating existing seed/fixture data
